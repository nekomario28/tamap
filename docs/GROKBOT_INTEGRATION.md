# TaMap × Grok Bot 統合案

対象：TaMap（stdio MCP サーバー `tamap/mcp_server.py`）を、Grok Bot の 4 体（TaMap PM＋3 体の専門Bot）にどう組み込むか。UX は [UX_DESIGN.md](UX_DESIGN.md) のとおりとし、ここでは「どの仕組みでつなぐか」と「各Botの指示文」を決める。操作用の Web UI・公開URL は使わない（例外は閲覧専用のライブページだけ。3.6 章）。

## 0. 確かさの区別

この文書では、各項目の確かさを次の 4 つのラベルで区別する。

- **【前提】**：Grok Bot の仕様として与えられている事実。この文書の作業では確認していない。
  - ユーザーが話すのはメインBot 1 体。
  - Bot は互いにメッセージを送れる（teammate）。
  - Bot ごとに指示文とメモリを持つ。
  - ユーザーの全Botが 1 台の永続 Linux box（ファイルシステム・シェル・uv/python）を共有する。
  - Bot は MCP コネクタとシェルコマンドを使える。
  - チャットは Markdown・mermaid・画像/GIF 添付・質問ウィジェット（ボタン最大 6、押したボタンの文がユーザーの返信になる）・絵文字リアクションに対応する。
  - 送信済みメッセージは編集できない。
  - Bot は定期実行（routine）を持てる。
- **【確認済み・P0】**：Grok Bot のチャットで確認済み（UX_DESIGN の P0）。mermaid は classDef・linkStyle・style・破線/太線・`<br>` を含めて正しく描画される。アニメーション GIF の添付は再生される。
- **【確認済み・開発VM】**：この PR の作業で、Grok Bot ではない開発用の Linux VM で実行して確かめたこと。`tests/test_core.py`・`tests/e2e_mcp.py`、`scripts/tamap_cli.sh` の呼び出し、GIF の生成と目視。
- **【未確認】**：上の 3 つ以外のすべて。Grok Bot の挙動について、【前提】を超えることは書かない。書く場合は【未確認】と付ける。

## 1. つなぎ方の選択肢

### 案A：stdio MCP サーバーを PM に登録する
- 登録するコマンドは `/workspace/tamap/scripts/mcp_server.sh`（`uv sync` で `.venv` を作っておく）。PM は `create_map` などをツールとして呼ぶ。
- 良い点：
  - 引数のスキーマとエラー（`isError`、`revision_conflict`）がそのまま渡る。
  - structuredContent（map_id・revision・diff・gif_path）を PM が読める。
  - チャット用のテキスト（mermaid ブロック）を、PM がそのまま貼れる。
- 懸念：Grok Bot の MCP コネクタが「box 上のローカルコマンドを stdio で起動する」形の登録に対応しているかは【未確認】。【前提】にあるのは「MCP コネクタを使える」ことだけ。リモート（HTTP）専用だった場合、この案は使えない。その場合も HTTP サーバーは足さず、案B に切り替える。
- 確かさ：
  - サーバー単体（公式 mcp クライアントで stdio 起動 → 全ツール呼び出し）は【確認済み・開発VM】。
  - Grok Bot からの登録・呼び出しは【未確認】。

### 案B：Bot がシェルで CLI を呼ぶ
- `scripts/tamap_cli.sh <ツール名> '<JSON引数>'` で、案A と同じ関数を呼ぶ。
  - 標準出力：チャット用テキスト（そのまま貼る）。
  - 標準エラー出力：structuredContent の JSON。
  - 終了コード：ツールがエラーを返したら 1。
- 例：`scripts/tamap_cli.sh simulate_delay '{"map_id":"JbeSRnxW","task_id":"T4"}'`
- 良い点：
  - 【前提】の「シェルコマンドを使える」「box を共有する」だけで動く。
  - MCP の登録の仕方に左右されない。
  - 専門Botにも同じ方法で使わせられる。
- 懸念：
  - Bot が JSON をシェルの引数に正しくクォートできるかは【未確認】。引用符を含むタイトルで壊れやすい。対策として、JSON をファイル（例：`/tmp/tamap_args.json`）に書き、標準入力から渡す形（`scripts/tamap_cli.sh create_map < /tmp/tamap_args.json`）を指示文で指定する。
  - 出力の読み取りは、Bot が標準出力と標準エラー出力を分けて受け取れるかに依存する【未確認】。
- 確かさ：
  - `tamap_cli.sh` の動作（別のディレクトリから起動しても動く、エラーで終了コード 1）は【確認済み・開発VM】（e2e に含む）。
  - Grok Bot のシェルからの実行は【未確認】。

### 案C：共有のスキルファイルに手順を書き、PM はそれに従う
- 指示文の本体（4.2 の文面テンプレート、ボタンの文、エラー処理）を、リポジトリのファイル（例：`/workspace/tamap/docs/GROKBOT_INTEGRATION.md` の 5 章）に置く。Bot の指示文には「分析の前にこのファイルを読む」とだけ書く。
- 良い点：
  - 指示文を git で管理できる。
  - 4 体の文面を 1 か所で直せる。
  - Bot の指示文の長さの上限に左右されにくい。
- 懸念：
  - Bot が毎回ファイルを読み直すかは【未確認】。
  - メモリに古い版が残る可能性がある【未確認】。
  - 案A・案B のどちらとも組み合わせられるが、単独ではツールの代わりにならない。

### 判断：案A を主にし、だめなら案B。指示文は案C で一元管理する
1. まず 6 章の疎通確認 1 で、案A（MCP 登録）を試す。
2. 登録できなければ案B に切り替える。指示文の「ツールを呼ぶ」の部分を「`tamap_cli.sh` を呼ぶ」に読み替えるだけで済むように、5 章の指示文はツール名と JSON 引数で書いておく。
3. 指示文の本体は案C としてリポジトリに置き、Bot の指示文には要点と参照先だけを書く（要点を直接書くのは、ファイルを読まなかったときの保険）。

## 2. 3 体の専門Botの引き継ぎ

### 推奨：PM を中心にした放射型（PM ⇄ 各専門Bot）
```mermaid
flowchart LR
  U(["ユーザー"]) -- 依頼 --> PM["TaMap PM"]
  PM -- "①分解の依頼" --> MA["🗺️ Map Architect"]
  MA -- "tasks JSON" --> PM
  PM -- "②影響の依頼（map_id）" --> RA["⚠️ Risk Analyst"]
  RA -- "起点ID＋対処案3件" --> PM
  PM -- "③検査の依頼（3アクション案）" --> QR["✅ Quality Reviewer"]
  QR -- "before/after" --> PM
  PM -- "結果1通＋GIF＋ボタン" --> U
```
- **書き込むのは PM だけ**。`create_map`／`update_map` を呼ぶのは PM 1 体にする。こうすると revision の競合が起きにくく、UX の「投稿は 2 つ」も PM だけで守れる。専門Botは JSON を PM に返すだけ。
- **Bot の状態の記録も PM がする**。依頼を送る直前に `set_bot_status(<専門Bot>, working)` を呼ぶ。このときコード側で PM が自動的に待機（「〜の結果待ち」）になる（P2）。返信を受けたら `set_bot_status(<専門Bot>, done)` を呼ぶ。こうすると、GIF の「PM→専門Bot（青い封筒）→PM（黄色い封筒）」の流れと、記録の順番が一致する。
  - 別案：専門Bot自身が `set_bot_status` を呼ぶ。時刻は正確になるが、3 体すべてにツールを持たせる必要がある。PM 側の記録と二重にならないよう、どちらか一方に決める。
- **中身の大きいデータは共有ファイルで渡してもよい**（【前提】の共有 box を使う）。例：MA が `data/handoff/<map_id>/map_architect.json` に書き、メッセージでは「書きました：<パス>」と伝える。まずは 2.1 のプレーンテキスト＋フェンスで渡し、メッセージが長すぎるときだけファイル渡しに切り替える。

### 2.1 依頼と返信の形（プレーンテキスト＋フェンス）

Bot 間のメッセージはプレーンテキストである（【前提】）。メッセージ全体を JSON にしてはいけない。実機では、PM が Quality Reviewer への依頼を JSON のまま送ろうとして、整形エラーで1回送れなかった。外側は文章、中身の構造化データはフェンス1つ、に分ける。

PM → 専門Bot（依頼）:

````text
Map Architect へ。次の文章をタスクに分解してください。ID が書いてあればそれを使い、無ければ T1 から振ってください。

```json
{"instruction": "…ユーザーの文章…", "map_id": "JbeSRnxW", "tasks": []}
```
````

- 最初の文字は `{` にしない。日本語の依頼文から始める。
- ` ```json ` フェンスは1つだけ。フェンスの外に JSON を重ねない。
- 改行や引用符はフェンスの中に置く。シェル引数のように外側でエスケープしない。

専門Bot → PM（返信）:

````text
地図、できたっす！

```json
{"title": "…", "tasks": [], "say": "地図、できたっす！"}
```
````

- フェンスは1つ。前に一言までなら書いてよい（`parse_handoff` が捨てる）。
- 末尾カンマや曲がった引用符（“ ”）が混ざっても、PM は自分で直さず `parse_handoff(text, bot)` に本文をそのまま渡す。自分で JSON を読まない。
- 成功したら `structuredContent.data` を使う。このツールの1行はユーザーには貼らない。
- 失敗したら、返ってきたエラーとヒントを添えて、そのBotに1回だけ送り直す。

`parse_handoff` は MCP ツールである（`scripts/tamap_cli.sh parse_handoff` でも同じ。CLI の許可リストは MCP のツール一覧から作る）。`bot` は `map_architect` / `risk_analyst` / `quality_reviewer`。`role` という引数名でも同じ。両方渡したときは一致している必要がある。
- **待ち時間**：UX は「60 秒応答なしでエラー表示」を前提にしている。しかし PM が teammate の返信を同じターンの中で待てるのか、それとも返信が別のターンとして届くのかは【未確認】。返信が別のターンとして届く場合は、PM は依頼を出したらいったんターンを終え、返信のたびに次の依頼を出す（状態は map の `bots` に残っているので、PM のメモリだけに頼らない）。

### 別案：数珠つなぎ（PM → MA → RA → QR → PM）
- 専門Bot同士で直接渡すので、PM を経由する回数が減る。
- その代わり、途中で止まったときに PM が気付きにくく、GIF の「PM と専門Botの往復」とも合わない。今回は採用しない。

## 3. Grok Bot の機能の使い方

- **質問ウィジェット**：【前提】ボタンは最大 6 個、押したボタンの文がそのままユーザーの返信になる。そのため PM の指示文では「この文が来たら、このツールを呼ぶ」を文字列で対応させる（5.1 の対応表）。ボタンの文には T 番号を入れる（「T4が遅れたら？」）。こうすると、自分で入力したときと同じ経路で処理できる。
- **GIF**：`render_flow_gif(map_id)` が `out/<map_id>_flow.gif` を書き、そのパスを返す。PM はそのファイルを結果の投稿に添付する。
  - GIF 添付の再生は【確認済み・P0】。
  - この PR の `render_flow_gif` が作ったファイルを Grok Bot で添付・再生できるかは【未確認】。
  - box に日本語フォントがあるかも【未確認】。見つからないときは、戻り値の 1 行に「文字化けの可能性」と出る。`TAMAP_FONT` でフォントを指定できる。
- **mermaid**：ツールの戻り値をそのまま貼る（【確認済み・P0】）。1 投稿に mermaid は 1 ブロックまで（UX_DESIGN 4.0）。
- **絵文字リアクション**：UX_DESIGN では状態の表示に使わない。使うとしても、ユーザーの入力に 👀 を付けて「受け付けた」を示す程度。Bot がユーザーのメッセージにリアクションできるかは【未確認】。
- **送信済みメッセージは編集できない**【前提】：途中の状態は投稿せずに記録だけしておき、結果は GIF 1 本で見せる（UX_DESIGN 4.1 案C）。
- **routine（定期実行）による再評価**：今回の MVP の範囲外（UX_DESIGN 8 章「後回し」）。入れる場合の案：
  - PM の routine で、毎朝 `list_maps` → 各 map の `get_map` を呼ぶ。条件は次の 2 つ。
    - ブロック中のタスクがある。
    - 最終更新から 24 時間以上たっている。
  - 条件に当てはまる map についてだけ、1 行と［チームで再分析］［T4が遅れたら？］のボタンを投稿する。
  - routine からは `update_map` を呼ばない。サーバー側でも、正規化のあとで tasks / analysis / title が同じ `update_map` は revision を上げない（7.1）。
  - 未確認の点：routine の実行がチャットに投稿できるか、どの会話に投稿されるか、ボタンを付けられるか、MCP やシェルを使えるか。すべて【未確認】。

## 3.5 キャラクター（4 体の個性と「かわいさ」）

レトロなドット絵の GIF の雰囲気は残したまま、4 体をキャラクターにした。見た目・口調・モチーフの正本は `tamap/persona.py`（コード）で、GIF・mermaid・指示文はすべてここに合わせる。
- デザインは TaMap 独自のもの。Grok Bot の公式のマスコットや見た目に合わせたものではない（Grok Bot の見た目の仕様は【前提】に無いため）。

**4 体の設定**（体は共通の丸いロボット。色とモチーフで見分ける）
- 📋 **TaMap PM**：まとめ役。藍色。旗つきアンテナとヘッドセット。しっかり者で明るく、丁寧語で話す。
  - 口ぐせ：「まかせてください！」「みんなの結果、待ってます…」「まとまりました！」
- 🗺️ **Map Architect**：地図職人。青緑。黄色いヘルメットと巻いた地図。無口で几帳面、「〜っす」と話す。
  - 口ぐせ：「線、つなぐっす。」「地図、できたっす！」
- ⚠️ **Risk Analyst**：心配性の探偵。琥珀色。虫めがねと「！」のアンテナ。「…かも」が口ぐせ。
  - 口ぐせ：「ここ、あやしいかも…」「影響の先、見つけました！」
- ✅ **Quality Reviewer**：赤ペン先生。ピンク。赤ペンとチェックのバッジ。やさしいけど見逃さず、「〜ね」と話す。
  - 口ぐせ：「ちょっとだけ直すね」「N件直したよ！」

**状態の表し方**（状態の色は今までどおり、待機＝灰／作業中＝青／完了＝緑／エラー＝赤）
- 待機：色がうすくなり、目を閉じて「zZ」。
- 作業中：その 1 体だけに青い光の枠が付き、ぴょこぴょこ跳ねて、キラッと光り、ときどきまばたきする。
- 完了：「^ ^」の笑顔とほっぺの赤み。
- エラー：「> <」の顔と汗。

**どこに出すか**
1. **流れの GIF**（`render_flow_gif`）：上の 4 体のドット絵が並ぶ。状態が変わるたびに、そのBotがふきだしで一言しゃべる。
   - ふきだしの文は、`set_bot_status` の `say`（30 文字まで）を使う。`say` が無ければ口ぐせを使う。
   - 事実（何をしているか）は、今までどおり下の字幕（note）に出す。
2. **チーム紹介の GIF**（新しいツール `render_team_card` → `out/tamap_team.gif`）：4 体が跳ねてまばたきする、約 1.7 秒のループ。
   - PM の最初の挨拶に添付する（UX_DESIGN 3.1 の挨拶＋サンプルのボタン）。
3. **Bot の稼働図（mermaid）**：各ノードを「📋 TaMap PM」のように絵文字つきの名前にし、状態の顔文字（`(-ω-)zz` 待機、`(•ω•)✧` 作業中、`(^ω^)` 完了、`(>ω<;)` エラー）を付ける。作業中・完了・エラーのBotには、ふきだしの一言も入れる（`say` があればそれ、無ければ口ぐせ。GIF とライブページと同じ）。待機は口ぐせを出さず、note（「〜の結果待ち」など）だけを出す。
4. **チャットの文面**：一言は「飾りの 1 行」だけにする。具体的には次の 3 か所。
   - 結果の「レビューで直した点」の見出しの後ろの一言。
   - エラー投稿の 1 行目。
   - 挨拶。
   - 結論・3 アクション・推定・未確認は、キャラの口調にしない（事実と推定を分けて書くルール〔UX_DESIGN 1.4〕を崩さないため）。

**確かさ**
- ドット絵・ふきだし・チーム紹介の GIF の生成と目視、mermaid（絵文字・顔文字入り）の描画：【確認済み・開発VM】。mermaid は headless Chrome＋mermaid v11 で、全 11 ブロックを描画した。
- 絵文字と顔文字が Grok Bot のチャットの mermaid で崩れないか：【未確認】（P0 で確認したのは classDef・linkStyle・`<br>` など）。
- ユーザーがキャラを「かわいい」と感じるか：【未確認】（Yuu さんの感想待ち）。

## 4. 確かさのまとめ

**確認済み**
- 【P0】Grok Bot のチャットで mermaid（classDef・linkStyle・style・破線/太線・`<br>`）が描画される。アニメーション GIF の添付が再生される。
- 【開発VM】
  - 全ツールの入出力（e2e 101 項目）。ライブページ（読み取り専用、SSE、headless Chrome でのドット絵の一致）。
  - 内容が同じ `update_map` は revision を上げない（`unchanged: true`、本文「変更なし（revision N のまま）」）。`expected_revision` が違うときは、中身が同じでも拒否する（unittest・e2e）。
  - `set_bot_status` と `update_map` の読み取り・変更・書き込みは、置き換えないロックファイル上の排他ロックの中で行う。複数プロセスが同時に `set_bot_status` しても、各 `note` の履歴は残る。同じ revision への `update_map` は1件だけ成功する（unittest）。
  - 稼働図は、作業中・完了・エラーに `say`（無ければ口ぐせ）を出す（unittest・e2e。`get_status` と `tamap_cli.sh` でも同じ）。

## 7. トラブルシューティング（実機の4ボットで出たもの）

2026-10-11 の実機（PM・Map Architect・Risk Analyst・Quality Reviewer が teammate として対話し、PM が TaMap の stdio MCP を呼んだ）で出た3件。下の対処は開発VMの unittest（26件）と e2e（94項目）で確認した。同じ4体でもう一度1周して確かめたわけではない【未確認】。

### 7.1 update_map が、中身が同じなのに revision を上げる

Map Architect が同じ tasks を返し、rev 1 が rev 2 になった。タスクも分析もタイトルも変わっていない。

対処: `update_map` は、渡した tasks / analysis / title を正規化した結果が現在と同じなら、ファイルを書き換えない。本文の1行目は「変更なし（revision N のまま）」。structuredContent の `unchanged` は true、`diff` は null、revision は N のまま。図は今のマップである。

`expected_revision` が現在と違うときは、中身が同じでも `revision_conflict` で拒否する。PM は `get_map` で読み直す（5.1）。

ユーザーへの文で「rev N → N+1」と書くのは、`unchanged` が false のときだけ。N はツールが返した revision を使う。自分で +1 しない。

正規化で同一とみなす例: status の「完了」と `done`、タイトルの前後の空白、`depends_on` の「T1、T2」と `["T1","T2"]`。タスクの並び順が違うときは、別の更新として revision を上げる。

### 7.2 専門Botへのメッセージが JSON の整形エラーで送れない

Bot 間はプレーンテキストなのに、PM が Quality Reviewer への依頼を JSON として埋め込んだため、送信が1回失敗した。

対処: 2.1 の形にする。依頼も返信も、日本語の文＋ json のコードフェンス1つ。PM は返信本文を `parse_handoff(text, bot)` に渡す（`role` でも同じ）。前置き、フェンス、末尾カンマ、スマートクォート（“ ” ‘ ’）はサーバーが除く。JSON がオブジェクトでない、必要な項目が無い、といったときはエラーとヒントが返る。それを添えて1回だけ送り直す。

`scripts/tamap_cli.sh parse_handoff` に `{"text":"…返信…","bot":"quality_reviewer"}` を渡しても同じ関数を呼べる。

### 7.3 set_bot_status に say を渡せない

PM のツール一覧に `say` が無かった。接続側が、キャラクター追加より前のスキーマをキャッシュしている。サーバーのコードには `say` がある。

対処（スキーマを更新しなくても動く）: `note` に一言を埋め込む。`note` は古いスキーマにもある。

- `set_bot_status(map_id, bot, status, note="受付 ｜ say:まかせてください！")`
- ASCII の `|` と全角コロン `：` でもよい。`A | B` のように `say:` が無い `|` は、事実の文のまま残る。
- JSON でもよい: `note='{"note":"受付","say":"まかせてください！"}'`。末尾カンマや “ ” も読める。文の末尾に `{"say":"一言"}` と付ける形も読める。
- `say` 引数を同時に渡したときは、引数の方を使う。note 側の印は事実の文から除く。
- 一言は30文字まで。それより長いときは切れる。

シェルが使えるときは、同じ関数を引数つきで呼べる。

`scripts/tamap_cli.sh set_bot_status '{"map_id":"…","bot":"pm","status":"working","note":"受付","say":"まかせてください！"}'`

ツール一覧が更新されたあとは、`say` を引数で渡してよい。どちらでもサーバーの動きは同じ。

## 8. トラブルシューティング（2回目の実機4ボットで出たもの）

2026-10-11、7章の修正のあとにもう一度4体で1周したときに残った3件。下の対処は開発VMの unittest と e2e で確認した。同じ4体でもう一度1周して確かめたわけではない【未確認】。

### 8.1 set_bot_status を同時に呼ぶと、片方の履歴が消える

PM が `set_bot_status(pm, working)` と `set_bot_status(map_architect, working)` を並列に呼んだ（stdio の呼び出しが別プロセスになりうる）。Map Architect 側の結果では PM が待機のまま「結果待ち」が無く、PM の履歴が一時的に消えた。後から書いた方が、先に書いた内容を知らないままファイル全体を置き換えていた。

対処: `create_map` / `update_map` / `set_bot_status` の読み取り・変更・書き込みは、すべて1つの排他ロックの中で行う。ロックは `data/maps/.lock`（`TAMAP_DATA_DIR` を変えたときはその中）に取る。このファイルは置き換えない。マップの JSON を `os.replace` で差し替える側にはロックを掛けない（差し替えると古い inode にロックが残り、次のプロセスは新しい inode を別のロックとして取ってしまう）。

並列でも、各 `note` の履歴は残る。専門Botを working にすると、PM がすでに待機中でも「<そのBot>の結果待ち」へ更新する。ただし PM の working が後から保存されると、PM は作業中のままになる。だから 5.1 のとおり、PM の working を先に、専門Botの working を次に、1つずつ呼ぶ。

### 8.2 稼働図が、完了したBotの say を出さない

`set_bot_status` / `get_status` の mermaid は、作業中（とエラー）のふきだしだけを出していて、完了に `say` を渡してもノードに載らなかった。GIF とライブページは完了でも一言を出す。

対処: 作業中・完了・エラーは、`say` があればそれを、無ければ口ぐせを「」で出す。待機は今までどおり note だけ。

### 8.3 専門Botの返信を、PM が自分でパースしていた

`parse_handoff` はサーバーの関数としてはある。PM はツールとして呼ばず、返信の JSON を自分で読んでいた。

対処: MCP ツール `parse_handoff(text, bot)` を使う（`role` でも同じ）。成功時は1行の説明と `structuredContent.data`。失敗時は `エラー:` と `ヒント:`、structuredContent の `ok: false` / `error` / `hint`。`scripts/tamap_cli.sh parse_handoff` も同じ関数を呼ぶ（許可リストは MCP のツール一覧）。専門Botの返信のたびに、本文をそのまま渡す（5.1・2.1）。
